Ejercicio · Arquitectura en la nube

Compra de tiquetes
de cine · 10K usuarios concurrentes

Diseño de un sistema que vende tiquetes con reserva de silla, sin permitir doble venta sobre la misma silla, con TTL de 10 minutos para completar el pago.

Usuarios

10.000 concurrentes (estreno tipo Marvel)

Acciones

Ver catálogo · Reservar · Pagar · Registrar

Restricción dura

Nunca doble reserva sobre la misma silla

TTL de reserva

10 minutos para pagar, si no se libera

01Diagrama por capas

Cada capa resuelve un problema concreto. Las peticiones bajan de arriba hacia abajo; cuanto más arriba se resuelve algo, menos carga llega al backend.

CAPA 01
Cliente
BROWSER / MOBILE

App Angular (SPA)

Lo que el usuario ve y toca.
  • Muestra catálogo, mapa de sillas, formulario de pago
  • Se conecta por WebSocket para ver sillas ocupadas en vivo
  • No habla directo con la pasarela ni la DB
Stack: Angular + TypeScript
↓ HTTPS
CAPA 02
Edge / CDN
CDN

CDN (CloudFront / Cloud CDN)

Red global de servidores cache.
  • Conecta al usuario con el servidor más cercano (menor latencia)
  • Sirve el catálogo cacheado: cartelera, películas, horarios
  • Evita 90% de peticiones al backend
  • Absorbe picos de tráfico (10K usuarios mirando cartelera)
AWS: CloudFront · GCP: Cloud CDN
STORAGE

Bucket de estáticos

Donde viven los archivos que no cambian.
  • HTML, CSS, JS de Angular compilado
  • Imágenes de películas, posters, logos
  • PDFs/QR de tiquetes ya emitidos
  • Barato, escalable, sin servidor
AWS: S3 · GCP: Cloud Storage (Blob)
WAITING ROOM

Sala de espera virtual

Filtro antes del backend.
  • Si llegan 10K, deja pasar 500 por minuto al sistema real
  • Los demás ven "Estás en posición 3.247..."
  • Protege al backend de un colapso
AWS: Waiting Room · GCP: Cloud Armor + contador
↓
CAPA 03
Puerta de entrada
API GATEWAY

API Gateway

La única puerta al backend. Todo pasa por aquí.
  • Valida el token del usuario (autenticación)
  • Rate limiting: máx 5 requests/seg por usuario
  • Enruta cada llamada al microservicio correcto
  • Evita: ataques DDoS, bots, abuso de la API
  • Evita: que el cliente hable directo con la DB
AWS: API Gateway · GCP: API Gateway / Apigee
WAF

Firewall de aplicación

Filtra peticiones maliciosas antes de que entren.
  • Bloquea SQL injection, XSS, bots conocidos
  • Reglas anti-revendedor (bloqueo por país/IP/patrón)
AWS: WAF · GCP: Cloud Armor
↓
CAPA 04
Lógica de negocio
(APIs)
SERVICIO

API de Catálogo

Películas, funciones, salas, sillas disponibles.
  • Lectura intensiva, casi nunca escribe
  • Sus respuestas se cachean en CDN
Stack: Node.js + TypeScript
SERVICIO

API de Reservas ⚡

El servicio crítico: bloquea sillas con TTL.
  • Recibe "quiero la silla A5 de la función 123"
  • Pregunta a Redis con operación atómica
  • Si nadie la tiene → la marca con TTL 10 min
  • Si ya está tomada → rechaza, sin esperar
Stack: Node.js + TypeScript
SERVICIO

API de Pagos

Conversa con la pasarela (Wompi, PayU).
  • Encola intentos de pago para no saturar la pasarela
  • Recibe webhook de confirmación
  • Confirma la reserva → genera tiquete
Stack: Node.js + TypeScript
DÓNDE CORRE

Cómputo (donde se aloja)

Las APIs anteriores corren aquí.
  • Opción serverless: Lambda / Cloud Functions
  • Opción contenedores: ECS Fargate / Cloud Run
  • Escala automático: de 1 a miles de instancias
AWS: Lambda / Fargate · GCP: Cloud Run
↓
CAPA 05
Datos
CACHE EN MEMORIA

Redis ⚡ (el corazón)

Base de datos en memoria RAM, ultra rápida.
  • Estado en vivo de sillas: qué silla está libre/reservada/vendida
  • Lock atómico: dos usuarios piden A5 → solo uno gana, el otro recibe "ocupada" en menos de 1ms
  • TTL nativo: la silla se libera sola a los 10 min si no pagó
  • Sesiones: tokens, contador de sala de espera
  • 100.000+ operaciones por segundo en un solo nodo
AWS: ElastiCache · GCP: Memorystore
BASE PRINCIPAL

Base de datos

Verdad histórica del negocio.
  • Películas, funciones, salas, usuarios
  • Tiquetes vendidos confirmados
  • Historial de transacciones
  • Solo escribe cuando el pago se confirma (no en cada intento)
SQL: PostgreSQL (RDS / Cloud SQL)
NoSQL: DynamoDB / Firestore
↓ eventos asincrónicos
CAPA 06
Asíncrono
(colas y eventos)
COLA

Sistema de colas

Buffer entre productores rápidos y consumidores lentos.
  • Recibe "intento de pago" y lo procesa cuando la pasarela pueda
  • La pasarela aguanta 100/seg, pero pueden llegar 5.000/seg
  • Evita perder peticiones si un servicio se cae
  • Desacopla servicios: la API de reservas no espera a la de pagos
AWS: SQS · GCP: Pub/Sub
ORQUESTADOR

Orquestador de flujos

Coordina pasos largos (la reserva dura hasta 10 min).
  • Paso 1: reservar silla en Redis
  • Paso 2: esperar pago hasta 10 min
  • Paso 3a: si pagó → confirmar, generar tiquete
  • Paso 3b: si no pagó → liberar silla, avisar usuario
AWS: Step Functions · GCP: Cloud Workflows
WEBSOCKET

Notificaciones en tiempo real

Empuja cambios al cliente sin que tenga que preguntar.
  • Cuando alguien reserva la A5, todos los demás la ven roja al instante
  • Evita 10.000 clientes preguntando "¿está libre?" cada segundo
AWS: API Gateway WebSocket · GCP: Cloud Run WS
NOTIFICACIONES

Email / Push

Envío del tiquete y avisos.
  • Manda el tiquete con QR al correo
  • Push si el pago falló o la reserva expiró
AWS: SES + SNS · GCP: SendGrid + FCM
↓
CAPA 07
Servicios externos
3RD PARTY

Pasarela de pagos

Procesa el dinero. No es parte de nuestro sistema.
  • Wompi, PayU, Mercado Pago, ePayco (en Colombia)
  • Devuelve webhook con resultado (aprobado / rechazado)
OBSERVABILIDAD

Logs y métricas

Para saber qué está pasando dentro del sistema.
  • ¿Cuántas reservas por minuto?
  • ¿La pasarela está lenta?
  • ¿Cuántas sillas se liberaron por timeout?
AWS: CloudWatch + X-Ray · GCP: Cloud Logging

02Flujo completo de una reserva

Recorrido de Ana, que quiere ver Avengers en la silla A5.

  1. Ana abre la app Angular. El CDN le entrega el HTML/CSS/JS desde el servidor más cercano (en milisegundos).
  2. La app pide el catálogo. Como ya está cacheado en el CDN, ni siquiera llega al backend.
  3. Ana elige la función. Se abre un WebSocket que muestra qué sillas están libres/ocupadas en vivo.
  4. Ana toca la silla A5. La app llama al API Gateway, que valida su token y aplica rate limit.
  5. El API Gateway enruta a la API de Reservas, que ejecuta una operación atómica en Redis: "marca A5 como reservada por Ana, TTL 10 min, solo si está libre".
  6. Redis garantiza que solo uno gana: Ana se queda con la silla. Si Carlos pidió a la misma vez, recibe "ocupada" inmediatamente.
  7. El WebSocket notifica a todos los otros 9.999 usuarios que A5 ya está ocupada.
  8. El Orquestador (Step Functions) arranca un flujo que esperará el pago hasta 10 minutos.
  9. Ana ingresa su tarjeta. La API de Pagos mete el intento en la cola SQS para no saturar Wompi.
  10. Un worker toma el mensaje, llama a Wompi, espera la respuesta.
  11. Wompi confirma vía webhook. La API de Pagos marca la silla como VENDIDA en Redis y persiste el tiquete en PostgreSQL.
  12. El Orquestador dispara: generar PDF/QR, guardarlo en S3/Blob, mandar correo vía SES.
  13. Si Ana NO hubiera pagado en 10 min: el TTL de Redis libera la silla sola, el WebSocket avisa a todos, y otro usuario puede tomarla.

03Reglas de oro del diseño

Cachear arriba

Cuanto más arriba (más cerca del usuario) se responde algo, menos carga llega abajo. El catálogo nunca debe pegarle a la DB en cada visita.

Operaciones atómicas

La regla "no doble reserva" se resuelve con UNA operación en Redis, no con "leer → pensar → escribir". Eso evita la condición de carrera.

Asíncrono cuando se pueda

El cliente no espera a que se mande el correo. Se encola y el servidor procesa cuando puede.

Desacoplar servicios

Si la pasarela se cae, las reservas siguen funcionando. Si el correo se cae, los pagos siguen. Cada servicio es independiente.

Una sola puerta

Todo el tráfico entra por el API Gateway. Nunca el cliente habla con la DB ni con la pasarela directamente.

Escala horizontal

En vez de un servidor gigante, muchos servidores pequeños que se multiplican según la demanda.
